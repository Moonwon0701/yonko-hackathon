## 목적

- 팀 회의에서 정한 협업 방식(테마별 브랜치 + 문원 통합)과 리더보드 제출 일정을 저장소 규칙 문서에 적어,
  세 명과 각자의 Claude Code 세션이 같은 규칙으로 움직이게 한다.

## 범위 — LLM이 한 것

- 프롬프트 1: 파일을 고치지 않고 비판적 검토만 했다. 컨셉 둘을 합치는 일은 git 병합이 아니라 새 전략 설계라는 점,
  통합 브랜치가 늘 뒤따라가야 한다는 점, 공용 코드 수정이 브랜치마다 갈라질 위험, 짧은 남은 기간을 지적했다.
  대안으로 컨셉을 `main` 안의 프로필 파일로 나누고 `sim` 대전으로 고르는 방식을 제안했다.
- 프롬프트 2: 팀이 정한 방식대로 문서를 고쳤다.
  - `CLAUDE.md`: "협업 방식: 테마 브랜치" 절을 새로 만들었다. 이 절에 담당·테마 표, 테마 브랜치 규칙, 리더보드 일정 표를 넣었다.
    테마 브랜치 규칙은 브랜치 안에서는 담당과 관계없이 전략 파일 수정, PR 없이 push, 문원이 `main`으로 옮김,
    공용 파일 버그 수정은 `main`에 PR, `git merge main`으로 받기, 제출 기록 남기기다.
    "PR 규칙", "누가 머지하는가", "LLM 사용 기록", "Git 규칙" 절에 테마 브랜치 예외를 더했다.
  - `README.md`: 같은 내용을 요약한 "협업 방식" 절과 일정 표를 넣었다. "매일 작업 순서"에 테마 브랜치용 순서를 더하고,
    "개발 규칙 요약"에 테마 브랜치 예외를 적었다.
  - 회의 메모에 없던 규칙은 LLM이 제안해 넣었다. 공용 파일 수정은 `main`으로 보내기, 제출한 커밋 기록하기,
    테마 브랜치에 LLM 기록 남기는 법, 테마 브랜치는 대회 끝까지 지우지 않기, 주인 아닌 사람의 테마 브랜치 작업 전 확인하기다.
  - 회의 메모의 "수요일 오후 12시"는 20:00 회차 결과를 보려면 자정이어야 해서 24:00경으로 해석해 적고, 문서에 그 해석을 밝혔다.

## 사람이 한 것

- 성혁·현진·문원: 회의에서 테마 분담(성혁 공격·확장, 현진 수비·자원 수급, 문원 통합 + 자체 개발)과 리더보드 제출 일정을 정했다.
  LLM이 제안한 "main 안 프로필 파일" 방식 대신 테마 브랜치 방식을 택했다.
- 문원: 회의 메모를 전달하고 문서 반영을 요청했다.
