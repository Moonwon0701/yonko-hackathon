## 개발 과정 — 협업 방식 (초안)

양식의 제출별 표 앞에 짧은 문단으로 넣는다(본문 4장 제한이라 5~6문장). 제출별 표의 "검증 방법"에도 "다른 테마 브랜치 기능을
스위치로 가져와 직접 대결"처럼 협업 흐름이 드러나게 쓴다.

> 3인 팀은 처음(9/21~9/27)에 코드를 입출력(adapter) → 상태(world) → 알고리즘 → 전략(strategy) 층으로 나누고 파일마다 담당자를
> 정했다. 9/28 첫 리더보드 뒤에는 한 봇을 같이 고치는 것보다 방향이 다른 봇을 나란히 키우는 편이 낫다고 보고, 각자 테마 브랜치를
> 맡았다: 성혁 공격·확장, 현진 수비·자원 수급, 문원 평가·튜닝과 통합. 테마 브랜치는 서로 막지 않고 자유롭게 고치되 `main`에는
> 직접 넣지 않았고, 문원이 상대 흉내 봇 풀·리그(라운드 로빈)·직접 대결 도구로 세 브랜치를 같은 조건에서 비교해 효과가 확인된
> 기능만 PR로 옮겼다(PR 57개). 다른 브랜치 기능은 기본값 "끔" 스위치로 들여와 하나씩 켜 보며 쟀다 — 현진의 별동대(현진 봇 상대
> 28 → 62%), 성혁의 점령 비용·건물 가치·호위 묶음, 성혁 hunters 중 기동대 수정만 채택. 모든 봇이 쓰는 파일(입출력·시뮬레이터)의
> 버그 수정은 테마 브랜치에 두지 않고 따로 `main`에 올려, 브랜치 비교가 버그 차이가 아니라 전략 차이를 재게 했다. 리더보드에는
> 회차마다 다른 브랜치 봇을 내(9/30 08:00 현진 봇, 20:00 통합 봇) 서버 결과로 다음 방향을 정했다.

근거: `CLAUDE.md` "협업 방식: 테마 브랜치"(9/28 회의 결정), [benchmarks.md](../benchmarks.md) "리그"·"서버 리더보드" 표,
